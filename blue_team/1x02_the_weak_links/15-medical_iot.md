## 1. BD Alaris Assessment (Finding 010)

Researched directly against **CISA ICS Medical Advisory ICSMA-20-317-01** ("BD Alaris 8015 PC Unit and BD Alaris Systems Manager"), the official advisory for CVE-2020-25165.

**Vulnerability described:** An Improper Authentication flaw in the network session authentication process between the BD Alaris PC Unit (PCU) and the BD Alaris Systems Manager. An attacker with network access to the affected devices can redirect the PCU's authentication requests, extract information from them, and complete a spoofed authentication handshake using custom code. Successful exploitation causes a denial-of-service condition, a drop in the PCU's wireless capability, forcing it into manual (non-networked) operation. CISA's advisory is explicit that **the pump continues to function as programmed** even when exploited. This is a communications/availability failure, not a dosing-manipulation vulnerability, an important distinction returned to in Section 3 below. What is lost is network-dependent functionality specifically: pre-populating infusion parameters via EMR interoperability, and wirelessly updating the Guardrails drug-safety limit database (DERS).

**A discrepancy worth noting directly:** CISA's own advisory records this vulnerability at **CVSS v3 6.5**, not the 7.5 the MedDefense scan report lists for Finding 010. This is flagged here explicitly rather than silently reconciled. It does not change the substance of the risk, but a SOC manager reading this alongside the original scan should know the authoritative vendor/CISA figure differs from the number the scan itself reports.

**Vendor-recommended mitigation, and whether MedDefense has implemented it:** BD's guidance has two distinct parts, and MedDefense has only followed one of them.

1. **Update to BD Alaris PCU version 12.1.2** (the remediated release, available since July 2021), **MedDefense has implemented this.** The scan directly confirms firmware 12.1.2 is running on all 7 scanned pumps.
2. **Enable the firewall on the Systems Manager server image and implement port/service restriction rules**, per BD's own product security whitepaper. **MedDefense has not implemented this**, and the scan itself proves it: Finding 010 explicitly recommends "isolate on dedicated VLAN with firewall restricting traffic to clinical workstations and PACS server only," which would not be a necessary recommendation if BD's own network-restriction guidance were already in place. The same finding separately confirms all 7 scanned pumps still have unchanged default web-interface credentials (admin/admin), a second, independent failure to follow basic device-hardening practice regardless of the CVE itself.

**Bottom line:** MedDefense followed the easier, single-action half of BD's guidance (a firmware update) and has not followed the harder, ongoing half (network isolation and access hardening). Exactly the kind of partial remediation that leaves a device technically "patched" while remaining practically exposed.

## 2. Philips IntelliVue Assessment (Finding 016)

**What data flows through these interfaces:** Port 2575/tcp is the HL7 (Health Level 7) interface, the standard messaging protocol used throughout healthcare IT to exchange clinical data between a bedside monitor and downstream systems (the EHR, central nursing-station displays, and alarm-management platforms). Through this channel flows a patient's continuous, real-time physiological data: heart rate, blood pressure, SpO2, respiration rate, temperature, and in many configurations ECG waveform data, associated with that patient's identifiers and timestamped continuously for the duration of monitoring. The exposed web management interfaces (ports 80/443) separately expose device configuration functions: network settings, firmware version, and, critically for patient safety, **alarm threshold configuration**, the limits that determine when the monitor alerts clinical staff to a dangerous vital sign.

**What an attacker with network access could see or do:** HL7 version 2.x, the version in near-universal use on legacy medical monitors of this generation, was designed under a "trusted network" assumption and **has no built-in authentication or encryption**, a fact independent of anything MedDefense configured incorrectly; it is a property of the protocol itself once network access is achieved. An attacker reaching this interface could therefore, at minimum, passively observe a live stream of a specific patient's vital signs, a direct confidentiality breach of continuous physiological PHI, not a one-time record but an ongoing feed. More seriously, because HL7 v2 does not authenticate the sender, an attacker could inject fabricated vital-sign messages toward the EHR or central station: a stable-looking false reading masking an actual emergency, or conversely a flood of false alarms designed to desensitize staff to real ones. Through the separately-exposed web interface, an attacker with access could reconfigure alarm thresholds directly, for example, raising a critical low-heart-rate alarm limit so a genuine deterioration event never triggers a notification at all. This is the point at which a "confidentiality" finding, if pursued further by an attacker, becomes a direct patient-safety finding.

## 3. Patient Safety Dimension

A compromised IT workstation puts data, availability, and organizational operations at risk (serious, costly, and disruptive) but ultimately recoverable through incident response, restoration from backup, and financial remediation. A compromised infusion pump or patient monitor puts a specific, physically present human being's immediate physiological safety at risk in a way no amount of post-incident recovery can undo. The worst-case scenario for a compromised workstation is data theft, service disruption, or a pivot point for further attack, bad, but bounded. The worst-case scenario for a compromised infusion pump is a falsified or withheld alarm, a corrupted drug-safety limit (the Guardrails/DERS database this exact BD vulnerability targets network access to), or, in a more severe hypothetical than anything confirmed in this specific CVE, a manipulated dosing parameter; outcomes measured in patient harm or death, not dollars or downtime, and not something a restore from backup can reverse.

## 4. Remediation Challenge: Why Patching Medical Devices Is Harder Than Patching IT Systems

**Regulatory:** Any modification to a medical device's software or firmware is potentially subject to FDA review, since the cleared device configuration is part of what was certified. This is not a hypothetical bureaucratic delay. BD's own public announcement of the 12.1.2 remediation release states plainly that the update "has not been reviewed or cleared by the FDA" at the time it shipped, illustrating that even the vendor's own emergency remediation exists in a regulatory gray area. A hospital cannot simply apply a firmware update the way it would an OS patch; it must weigh whether doing so affects the device's cleared status at all.

**Operational:** An infusion pump or patient monitor cannot be taken offline for a maintenance window the way a server can. Patching frequently requires physically removing the specific unit from clinical service, substituting a spare device for the patient currently connected to it, and coordinating that substitution around real-time clinical care, a materially different operational burden than scheduling an off-hours server reboot, and one that scales with the size of the device fleet rather than shrinking with automation the way IT patch management typically does.

**Vendor dependency:** Hospitals generally cannot modify medical device firmware themselves, even when technically capable of doing so. Only the vendor (BD, Philips) can issue an approved update, and the hospital's remediation timeline is entirely dependent on the vendor's own release schedule, testing cycle, and continued willingness to support that specific device model. If a vendor discontinues support for an older model (a real possibility across a fleet where, per this scan's own data, MedDefense's Philips monitors alone span firmware versions from 2019 to 2022) no future fix becomes possible at all, regardless of severity, echoing the same permanent-exposure dynamic already documented for MedDefense's EOL IT systems in this project's Task 12.

**A fourth factor worth naming directly:** fleet heterogeneity. Unlike a standard IT patch rollout targeting one OS across many identical machines, a medical device fleet accumulates different models and firmware versions purchased across years. This scan's own finding on the Philips monitors documents exactly that fragmentation across just the 13 devices it could reach. A uniform patching strategy essentially does not exist for a fleet this varied; each firmware generation may require its own separate vendor validation and rollout plan.
