## Reconciliation notes

### 1. Assets found in the network scan with NO prior documentation (shadow IT / undocumented)

- **A-012 - UNKNOWN-01 (10.10.2.99):** A Linux 4.x host on the Central servers subnet, running SSH and two unidentified web services (ports 8888, 9090). Never appeared in the IT asset list, Marcus's notes, or any other prior source. Sarah's best guess ("could be Marcus's or the intern's") is speculation, not confirmation. **This should be treated as a priority investigation item**: an unidentified host on the same subnet as the domain controllers and EHR database is a significant unknown.
- **A-024 - Unknown device (10.10.10.200), Westside:** A Linux 5.x host with port 3000 open (commonly associated with Grafana or a Node.js application), also undocumented anywhere. Sarah suspects an informally deployed monitoring tool, but this is unconfirmed.
- **A-023 - WS-WC-XRAY:** Not itself a network anomaly (it's a legitimate clinical workstation), but it was never captured in the original IT asset export from Task 0, even though the HR onboarding guide explicitly lists X-ray imaging as a Westside service. This is a documentation gap rather than a true shadow-IT case. The device is presumably known to clinical staff, just never inventoried by IT.

### 2. Assets mentioned in documentation that do NOT appear in the network scan

- **A-021 - Physician iPads (~25 units):** Referenced consistently across the onboarding packet and the Sophos report (explicitly out of MDM scope), but **no iOS devices appear anywhere in the scan output**. This could mean they were off-network (personal cellular data) during the scan, connect only intermittently, or use a network path Sarah's scan did not cover. This gap should be explicitly investigated rather than assumed benign, since it means MedDefense currently has **zero technical visibility** into these devices.
- **A-033 - CT Scanner (GE Revolution):** No distinctly named CT scanner host appears in the Radiology portion of the scan (only WS-RAD-01 and WS-RAD-02 are listed by name). It is possible the CT scanner's control workstation is one of the ~290 "additional" Central workstations omitted for brevity in the scan summary, that it was powered off during the scan, or that it doesn't communicate over this network segment at all. Its operating system remains undocumented across every source reviewed in this project.
- **Possible second Westside server:** Marcus's notes (Task 0) referenced a possible undocumented second server in the Westside closet, mentioned by Mike Torres but never confirmed. The Westside subnet scan shows only **ws-srv-01** as a server-class host. This is reasonably strong (though not conclusive) evidence that either the second server does not exist, was powered off during the scan, or sits on a network segment outside the scanned range.

### 3. Discrepancies or contradictions between sources

- **print-srv-01 status resolved:** Task 0 flagged this server as `[UNVERIFIED]', not physically confirmed in over a year. The network scan confirms it is active and responding on 10.10.2.31. This specific Known Unknown from Task 0 is now resolved; the server exists and is in active, unpatched use.
- **billing-srv-01 support status (new detail, not a contradiction):** The scan adds a detail absent from Task 0: standard Ubuntu 18.04 support ended in June 2023, and Extended Security Maintenance was never activated. This sharpens (rather than contradicts) the existing concern about this server, which has already been compromised twice.
- **Endpoint counts minor discrepancies, likely explained by the scan's own caveats:** Westside shows roughly 36 explicitly numbered workstations in the scan versus ~45 reported in the HR onboarding guide (Task 0); HQ laptops show ~25 in the scan versus ~30 in Task 0. Sarah's own notes acknowledge devices may have been powered off during the scan and that laptops are intermittent by nature. These gaps are plausible and not necessarily contradictions, but they have not been independently reconciled and should be treated as approximate, not exact, counts.
- **Network segmentation, independently confirmed, not contradicted:** Marcus's notes (Task 0/2) described Central as a flat network with no VLANs, based on his own review. The network scan independently confirms this empirically: "all subnets were reachable from the scan host... without any access restrictions." This upgrades the finding from a documented observation to a technically verified fact.
- **New exposure details not previously captured:** The scan surfaces 2 specific technical findings that existing documentation only described in general terms. (1) MySQL (3306) on billing-srv-01 is reachable from the entire internal network, mirroring the already-known PostgreSQL exposure on ehr-db-01, meaning this is a pattern affecting at least two critical database services, not an isolated case; and (2) the BD Alaris infusion pump firmware (v12.1.2) has a specific, vendor-disclosed security bulletin (issued 18 months ago) recommending network isolation, which has not been implemented. This gives the medical-device risk already flagged in Task 3/5 a concrete, vendor-confirmed basis rather than a general architectural concern.

This registry should now serve as the single reference point for all subsequent prioritization and remediation work in this project. Any future task referencing "an asset" should use the Asset IDs defined here.
